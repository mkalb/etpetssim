# Localization Instructions

Rules for the resource bundles in `i18n` and the localization key constants; repository-wide and Java instructions
still apply.

## Bundle Content

- Keep all production bundles (`messages_*.properties`) in sync: every bundle contains the same keys, and each key has
  the same placeholders in every bundle.
- `.url` keys exist in all bundles; an empty value means that the locale has no link. Their values are
  locale-specific links and are exempt from placeholder parity, because URLs may contain percent-encoding.
- Use indexed placeholders (`%1$s`, `%2$d`, `%1$.0f`); the order of the placeholders in a value may differ between
  the locales. In a value with placeholders, write a literal percent sign as `%%`.
- Label texts carry no trailing colon; views add a separator where a layout needs one (e.g., `LABEL_SEPARATOR` in
  `AbstractObservationView`).

## Key Schema

- A key consists of dot-separated segments of lowercase letters and digits, without other separators
  (`gridedgebehavior.blockxwrapy`).
- The first segment names the owner of the key:
    - an application area (`about`, `alert`, `args`, `header`, `window`),
    - an area shared by the simulations (`config`, `control`, `notification`, `observation`, `simulation`),
    - an enum, named after its type in lowercase (`cellshape`, `gridedgebehavior`); `CompassDirection` uses `compass`,
    - a simulation or the special package `start`, named after its package (`conway`, `wator`, `start`), followed by
      its area (e.g., `config`, `entity`, `observation`, `toolbar`).
- Use the standard suffixes: `.label` for the type label of an enum, `.tooltip`, `.prompt`, `.title`, `.subtitle`,
  and `.url`; entity descriptors use `.short`, `.long`, `.description`, and `.emoji`.
- Enums and records provide their keys as `java.md` ("Enums") describes; an enum uses the type label `<enum>.label`
  and keys with the same prefix for its constants (`cellshape.triangle`).

## Format and Editing

- Bundles are UTF-8 without BOM, without `\uXXXX` escapes, comments, or blank lines, with one consistent line ending
  and exactly one trailing newline.
- Each line holds one `key = value` entry; the entries are sorted alphabetically by key (case-insensitive), and the
  `=` signs are aligned in one column.
- Add, rename, or remove an entry by hand in all production bundles in the same change; put a new or renamed key at
  its sorted position and pad it so that its `=` stays in the existing column. Do not reorder or re-align existing
  entries by hand.
- Run the `i18n-consistency` skill once before finishing a change to a production bundle. Its report on format and
  parity is read-only; its `fix` mode reformats the bundles (e.g., when a new key does not fit the `=` column) only
  after confirmation by the user.

## Test Bundles

- The test bundles `test_messages_*.properties` (prefix rule in `junit.md`) are fixtures for `AppLocalizationTest`
  and deviate intentionally from the production bundles: `onlyUS` exists only in `en_US`, and `Hello %d` is not
  indexed.
- Only the format conventions apply to them; do not align their keys or placeholders with the production bundles.

## Key Constants

- Place key constants as `java.md` ("Code Style") describes; `AppLocalizationKeys` holds only the keys of `core`, `ui`,
  and the root package, and a simulation-specific key is a private constant of the class that uses it.
- Name a key constant after its key in upper snake case and split compound segments into words
  (`wator.config.sharkmaxage` -> `WATOR_CONFIG_SHARK_MAX_AGE`). A catalog class may name its label keys by role
  instead (`PATTERN_LABEL_KEY_*` in `ConwayPatterns`).
- Sort and test the key constant classes as `java.md` ("Utility Classes") describes; their tests also check that
  every key exists in all production bundles (`junit.md`, "Common Contract Patterns").
- The type Javadoc of a key constant class describes only its own keys.
- Access bundles only through `AppLocalization`.
